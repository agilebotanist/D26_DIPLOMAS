## RefAgent: A Multi-agent LLM-based Framework for Automatic Software Refactoring 

- **Summary:** RefAgent is a multi-agent system for end-to-end software refactoring. It has specialized agents for planning, executing, testing, and self-reflection. Authors evaluated it on 8 open-source Java projects.   
  Results: median unit-test pass rate 90%, code smells reduced by 52.5%, and reusability improved by 8.6%. Compared to single-agent baselines, RefAgent gives \+64.7% better unit test pass rate.  
- **Link:** [https\://arxiv.org/abs/2511.03153](https://arxiv.org/abs/2511.03153)

## Agentic Refactoring: An Empirical Study of AI Coding Agents

- **Summary:** A large-scale empirical study based on the AIDev dataset. The paper looks at how agents actually refactor in real open-source projects. Authors analyzed 15,451 refactoring instances from 12,256 pull requests and 14,998 commits in Java code, all generated by AI coding agents (Codex, Cursor, Claude Code, Devin).  
- **Link:** [https\://www\.researchgate.net/publication/397441947\_Agentic\_Refactoring\_An\_Empirical\_Study\_of\_AI\_Coding\_Agents](https://www.researchgate.net/publication/397441947_Agentic_Refactoring_An_Empirical_Study_of_AI_Coding_Agents)

## A Multi-Agent LLM Environment for Software Design and Refactoring: A Conceptual Framework

- **Summary:** A conceptual framework where multiple specialized "expert" LLM agents (performance, security, UI/UX, maintainability) collaborate or compete using consensus or auction protocols to produce design and refactoring recommendations. Includes formal definitions of agent interactions, sequence diagrams, and complexity analysis.  
- **Link:** [https\://www\.researchgate.net/publication/391205436\_A\_Multi-Agent\_LLM\_Environment\_for\_Software\_Design\_and\_Refactoring\_A\_Conceptual\_Framework](https://www.researchgate.net/publication/391205436_A_Multi-Agent_LLM_Environment_for_Software_Design_and_Refactoring_A_Conceptual_Framework)

# То что искал в F-26

## Geipel & Schweitzer — Software Change Dynamics

В работе сравнили граф зависимостей с реальными изменениями в ходе разработки

- \> половины зависимостей не участвует в изменениях  
- 10% активных зависимостей дают \>половины распространений изменений  
- Можно различать активные и не активные зависимости, чтобы прогнозировать и классифицировать ошибки агента

## Nord et al. — Propagation Cost

В работе проверили метрику Propagation Cost (PC) на изменениях в слоистой архитектуре

- Голый PC не замечает трансформацию: до и после значение одинаковое, тк эта метрика игнорирует семантику зависимостей  
- Вариации PC с весами начинают различать хорошую и плохую трансформацию

## Ribeiro et al. — Analyzing Class and Crosscutting Modularity with DSMs

Сравнили три версии одной системы через DSM и ввели понятие semantic dependencies – зависимости, которые не видны в коде, но реально существуют

- Синтаксические зависимости (видимые в коде) – это не полная картина. Есть еще семантические: один класс не ссылается на другой, но зависит от него поведенчески  
- Design rules (явные контракты между модулями) снижают и синтаксические, и семантические зависимости (можно использовать как ручную метрику поломки: сначала сформулировать правила и потом после рефакторинга проверить их, хотя это звучит тяжело для большого проекта)  
- ошибки агента можно делить на похожие классы: минус синтаксис, минус синтаксические зависимости, минус семантические (код вроде работает \+ тесты проходят, но поведение уже может не соответствовать ТЗ).

## MacCormack, Rusnak & Baldwin — Exploring the Structure of Complex Software Designs

Первоисточник для Propagation Cost. Посчитали DSM по вызовам функций в open-source и проприетарном коде и ввели visibility matrix

- Propagation Cost считается как плотность матрицы видимости, то есть сколько всего в системе достижимо из одной точки — это ровно «насколько одно изменение тянет за собой остальное»  
- Главный вывод: распространение изменений крайне неравномерно, небольшая часть дизайна отвечает за большую долю всех зависимостей — подтверждает идею «активных» узлов из Geipel  
- Базовая работа для главы с метриками, на неё ссылаются почти все остальные — цитировать обязательно  
- [https\://scispace.com/pdf/exploring-the-structure-of-complex-software-designs-an-4dxdxbabyj.pdf](https://scispace.com/pdf/exploring-the-structure-of-complex-software-designs-an-4dxdxbabyj.pdf)

## Baldwin, MacCormack & Rusnak — Hidden Structure: Using Network Methods to Map System Architecture

Продолжение той же линии на большой выборке проектов: посчитали Propagation Cost и посмотрели на форму графа

- Показали, что архитектура почти всегда «ядро-периферия»: маленькое плотное ядро и разреженная периферия, и именно ядро определяет стоимость изменений  
- Полезно как аргумент, что одну цифру по всей системе мало — нужна ещё и форма, то есть где именно плотность  
- Даёт готовый способ описывать результат: не «PC вырос на 3%», а «ядро выросло и в него вошли модули X и Y»  
- [https\://www\.hbs.edu/ris/Publication%20Files/13-093\_3011858c-cd52-494b-b58b-f46af7331e85.pdf](https://www.hbs.edu/ris/Publication%20Files/13-093_3011858c-cd52-494b-b58b-f46af7331e85.pdf)

## Wong, Cai, Kim & Dalton — Detecting Software Modularity Violations

Ввели Modularity Violations (MV) — нарушения того, как классы должны пользоваться чужими модулями

- Идея: если класс A лезет внутрь модуля B в обход его фасада, это ловится по шаблону «кто кого вызывает», а не по метрикам размера и связности  
- Ближайший родственник нашего блока «нарушения заданных правил», только правила выводятся из истории, а не задаются руками  
- Полезно как ответ на вопрос «а почему не считать просто нарушения по графу зависимостей» — MV ловит то, что граф модулей не видит  
- [https\://web.cs.ucla.edu/\~miryung/Publications/icse11-modularityviolation.pdf](https://web.cs.ucla.edu/~miryung/Publications/icse11-modularityviolation.pdf)

## Cordeiro, Noei & Zou — An Empirical Study on the Code Refactoring Capability of Large Language Models

Сравнили рефакторинги StarCoder2 и разработчиков на 30 open-source Java-проектах

- Результат, важный для нас: LLM делает много мелких переименований и извлечений методов, но реже берётся за структурные изменения и хуже с ними справляется  
- Это независимое подтверждение «агент полирует поверхность, а не перестраивает» — и обоснование, почему архитектурные метрики после агента вообще стоит мерить
