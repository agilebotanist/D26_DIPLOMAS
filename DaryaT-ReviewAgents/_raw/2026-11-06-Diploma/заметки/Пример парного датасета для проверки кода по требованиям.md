## Суть концепции

Для каждого текстового требования авторы сопоставляют две реализации: корректную и с ошибкой. Это позволяет оценивать и пропуск дефектов, и ложное отклонение корректного кода.

По описанию статьи, набор содержит более 700 задач и более 1400 отдельных примеров для оценки — по две версии кода на задачу.

| Основа | Как получены пары |
| --- | --- |
| HumanEval-X-Bugs из HumanEvalPack | Готовые корректная и дефектная реализации с описанием задачи и разметкой ошибки. |
| MBPP | Корректные решения дополнили ошибочными; часть функций восстановили из дефектного фрагмента и оставшейся части корректного решения. |
| QuixBugs | Использовали известную дефектную реализацию и её исправленную версию. |

В описанной разметке `1` означает корректный код, `0` — код с ошибкой. Для дефектных версий предусмотрены тип ошибки (`bug_type`) и её проявление (`failure_symptoms`), например неверный результат или ошибка выполнения.

В основном эксперименте модель получает требование и одну версию кода, без тестов и второй реализации. Это короткие самостоятельные функции на Python; применимость такого набора к ревью целых PR нужно оценивать отдельно.

Данные опубликованы в [репозитории авторов](https://github.com/HollinJ3177/Are-LLMs-Reliable-Code-Reviewers-Systematic-Overcorrection-in-Requirement-Conformance-Judgement/tree/main/dataset). [README](https://github.com/HollinJ3177/Are-LLMs-Reliable-Code-Reviewers-Systematic-Overcorrection-in-Requirement-Conformance-Judgement#expected-dataset-format) описывает парную запись с `task_id`, текстом требования, `canonical_solution` и `buggy_solution`; тесты указаны как необязательные поля для фильтра проверки исправлений.
