> [!note] Предварительная подборка
> Информация о датасетах и оценки их пригодности собраны и оформлены Codex; человеком они ещё не проверены. Это стартовая подборка для дальнейшего разбора: сведения и выводы будут уточняться, список — дополняться, а неподходящие наборы — исключаться.

Наборы данных для оценки ревью изменений backend HTTP/REST API и gRPC: реализации, тестов и документации. Наборы, посвящённые поиску уязвимостей, не рассматриваются; в смешанных наборах нужны примеры вне security-задач.

В таблице указаны размеры исходных наборов, а не число подходящих для диплома примеров. Публикация набора компанией и происхождение кода — разные характеристики: Microsoft, Alibaba, Ant Group и GitHub в перечисленных релизах используют открытые проекты. Это не выгрузки их внутренних ревью.

Для итоговой оценки не рассматриваем обучающие части наборов и корпуса, чей формат не позволяет проверить нашу систему на изменении с репозиторным контекстом. Исключённые варианты кратко перечислены ниже, чтобы не возвращаться к их повторному разбору.

Использование оставшихся данных для обучения конкретных моделей **пока не проверено**. Наличие тестовой части не гарантирует, что модель не видела исходные публичные PR. После выбора моделей нужно проверить раскрытые сведения об их обучении и исключить известные пересечения с оценочными примерами; неустранимую неопределённость учесть как ограничение. Одно название split недостаточно для вывода: у [AACR-Bench](https://huggingface.co/datasets/Alibaba-Aone/aacr-bench) единственная часть называется `train`, хотя сам набор опубликован как оценочный бенчмарк.

## Резерв

- **[SWE-PRBench](https://huggingface.co/datasets/foundry-ai/swe-prbench)** — 350 PR из 65 репозиториев с контекстом и историческими замечаниями. В отдельных проверенных примерах замечание уже исправлено в сохранённом итоговом патче. Нужна проверка соответствия ревизий или восстановление более раннего состояния; до этого набор не включаем в основной отбор.
- **[SWE-Review-Bench (Lego-X)](https://huggingface.co/datasets/Lego-X/SWE-Review-Bench)** — 1 384 сгенерированных патча для 500 задач SWE-bench Verified. Проверяется решение задачи по тестам, а не полнота замечаний о реализации, тестах и документации. Возможен как дополнительная проверка, если она понадобится; реальных авторских PR не заменяет. См. [[Пример датасета SWE-Review-Bench]].

## Исключены из текущего отбора

- **[CodeReviewer](https://zenodo.org/records/6900648)** — наборы обучения и оценки для отдельных задач работы с локальными фрагментами diff. Его обучающие части не рассматриваем; тестовые части также не выбираем из-за несоответствия формату агентского ревью полного изменения. [Описание задач и разбиений](https://arxiv.org/pdf/2203.09095).
- **[ContextCRBench](https://arxiv.org/abs/2511.07017)** — оценочный бенчмарк локальных фрагментов с контекстом файла/функции; документационные файлы фильтруются. Исключён из-за формата задачи, а не на основании подтверждённого обучения моделей на этих данных.
- **[CRAVE](https://huggingface.co/datasets/TuringEnterprises/CRAVE)** — предназначен для обучения и оценки решения APPROVE / REQUEST_CHANGES. Для нашей оценки обнаружения конкретных проблем одного итогового решения с пояснением недостаточно; готового полного перечня дефектов нет.
- **[SWE-CARE, dev](https://huggingface.co/datasets/inclusionAI/SWE-CARE)** — 7 086 примеров для разработки/обучения; не включаем их в итоговую оценку. В кандидатах оставлена только часть test.

## Примеры, которые уже просмотрены

- **ReviewBench, `brexhq/CrabTrap#15`.** В [опубликованной разметке](https://raw.githubusercontent.com/review-bench/ReviewBench/main/golden/brexhq_CrabTrap_15-5ef0884c.json) подтверждены замечания о возврате HTTP 200 при ошибке запроса к БД, непередаче отмены HTTP-запроса в запрос к БД и отсутствии проверки ветки пагинации `has_more=true`. Это примеры реализации и тестирования HTTP API, а не поиска уязвимостей. Корректность разметки пока не воспроизводилась запуском.
- **CR-Bench-Verified, Django.** В [записях набора](https://huggingface.co/datasets/rghosh8/cr-bench-verified) найдены: `bug_origin_pr=7482` — необязательные URL-параметры попадают в kwargs как `None`; две разные записи с `bug_origin_pr=13134` — редирект теряет префикс пути или query string. Это серверная HTTP-маршрутизация, но не готовое покрытие контрактов прикладных REST API.
- **SWE-PRBench, `linkding__1261`.** Историческое замечание о замене абсолютного API URL на относительный относится к файлу, отсутствующему в сохранённом итоговом diff. Это пример, почему соответствие замечания ревизии нужно проверять до включения записи в эталон.

## Что найдено у крупных компаний

Помимо рассмотренных релизов, есть большие корпуса коммуникации и закрытые промышленные исследования. Например, [Chromium Conversations](https://meyersbs.me/chromium-conversations/) содержит более 1,5 млн комментариев проекта Google Chromium, но опубликован для анализа обсуждений и реакции на замечания; комплект снимков кода для нашего эксперимента не подтверждён. Это исследовательский сбор данных Chromium, а не релиз внутренних ревью Google.

В [публикации Google о разрешении замечаний ревью](https://research.google/pubs/resolving-code-review-comments-with-machine-learning/) описываются внутренние данные и производственное применение. Публичная выгрузка соответствующих PR и комментариев в просмотренных материалах не найдена. Масштаб внутреннего исследования нельзя указывать как объём доступного датасета.

## Следующий шаг отбора

В первую очередь проверить backend API-примеры **ReviewBench и AACR-Bench**; **CROP** рассмотреть как более крупный источник для самостоятельного отбора. **SWE-CARE** проверить отдельно для реализации, учитывая фильтрацию замечаний о тестах и документации. Это предварительный порядок просмотра, а не выбор итогового датасета.

Для выбранных примеров нужно установить соответствие замечаний ревьюируемой версии, проверить основания замечаний и лицензионные условия, затем посчитать покрытие реализации, тестов, документации и протоколов. Ложное замечание не делает весь PR корректным; отсутствие исторического замечания также не доказывает отсутствие ошибки.
