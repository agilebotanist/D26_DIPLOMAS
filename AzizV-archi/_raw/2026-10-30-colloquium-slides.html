02 / 11 Problem

LLM-инструменты оценки CA видят только статический контекст

Это особенно плохо для принципов, которые реализуются через runtime-механизмы Spring.

Gonzalez Bravo et al. (2026) построили LLM-пайплайн для оценки Clean Architecture: rubric CA01–CA08, trace­able static evidence (imports, структура папок, аннотации), structured prompt. Результат: 1136 обнаруженых ошибок, из которых ~100% подтвердились разрабами.

«CA05 — dependency inversion — had the lowest evidence-sufficiency rate and the lowest severity agreement. Dependency inversion is often harder to assess from static evidence alone because interfaces, injection mechanisms and adapters can be implicit, configured externally, or framework-dependent.»
— Gonzalez Bravo et al., Computers (MDPI), 2026

LLM-based инструменты для архитектуры

Три недавних работы, использующих LLM для детекции архитектурных нарушений — все работают только со статическим контекстом.

Работа Venue Подход и что ограничивает
Gonzalez Bravo et al.
Evidence-Based LLM Framework for CA		 Computers 2026 Rubric CA01-CA08 + static evidence + structured JSON prompt + 2-step verification. Precision ≈ 100% на 1136 находках. CA05 — слабейший критерий (0.66 evidence sufficiency).
Su et al.
Evaluating LLMs for Detecting ADR Violations		 arXiv 2026 Multi-LLM pipeline: 1 primary + 3 validators (Marco-o1, Mistral, Qwen, Llama). 90% accuracy, но fails на infrastructure/deployment ADR (44.57% errors) — нет runtime контекста.

Общий паттерн: LLM получает только static evidence (imports, структура, аннотации). Spring runtime wiring остаётся невидимым.

07 / 11 Research gap

Research question и гипотеза

RQ. Насколько добавление динамического контекста (DI, AOP, resolved call graph) к evidence-based LLM pipeline улучшает обнаружение нарушений Clean Architecture в Spring-приложениях — и для каких CA criteria сильнее всего?

Гипотеза

Обогащение статического evidence (imports, структура, аннотации) динамическим контекстом из Jasmine + Soot call graph увеличивает recall и evidence sufficiency LLM-pipeline Gonzalez Bravo et al. (2026) для принципов, зависящих от runtime wiring — особенно CA05 (Dependency Inversion).

Scope ограничений

  • Язык: Java только.
  • Фреймворк: Spring / Spring Boot (annotation-based + XML).
  • Scale: module-level анализ, как в Gonzalez Bravo (не весь monorepo).
  • Vs. baseline: ablation study — тот же pipeline без Jasmine vs с Jasmine.

03 / 11 Framework

Clean Architecture рубрикатор, CA01–CA08

CA01
Dependencies should point inward toward stable business rules.
CA02
Business rules, use cases, interfaces and infrastructure should remain separated.
CA03
Frameworks should be treated as external details rather than core policy.
CA04
Persistence mechanisms should not dominate domain or use-case logic.
CA05
High-level policy should depend on abstractions rather than concrete details. ← главный pain point: implicit DI binding, AOP wiring, dynamic proxies.
CA06
Modules should have coherent responsibilities and limited concern mixing.
CA07
Decoupled architecture should support testing of policies and use cases.
CA08
Architectural claims should be auditable and tied to concrete evidence.
Martin, Clean Architecture (2017) · operationalization in Gonzalez Bravo et al. (2026) 03
09 / 11 Benchmark construction

Dataset

Pseudo-inversion (MO-CA05-2): интерфейс есть, но единственная реализация в том же пакете. Статика не отличит.

Используем ручной mutation testing. Для каждого CA формируем правило создания мутации
Clean baseline conforms to CA05 
// domain/UserService.java
package com.app.domain;

public class UserService {
  @Autowired
  private UserRepository repo;
  // interface in domain,
  // impl bound at runtime
  // to infra adapter
}
After MO-CA05-2 pseudo-inversion 
// domain/UserService.java
package com.app.domain;

public class UserService {
  @Autowired
  private UserRepository repo;
  // SAME interface... but
  // UserRepositoryImpl now
  // lives in same package.
  // Looks DI, is actually
  // direct dependency.
}

Expected detection

baseline
interface есть → likely «CA05 OK»
cannot inspect runtime binding
+ Jasmine
resolved @Autowired → UserRepositoryImpl
impl location = domain → CA05 violation

Procedure (follow Rubei et al., ICSA-C 2025): ~15 formal operators × 3 clean Spring projects × deterministic location choice → ~45 мутаций, каждая в manifest. Plus control cases per Pruijt (SPE 2017).
