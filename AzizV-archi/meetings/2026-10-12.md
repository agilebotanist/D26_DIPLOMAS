# Азиз Вундиров — встреча 2026-10-12

**Итог:** Тема нашла направление, и руководитель его одобрил: динамический (runtime) контекст Spring-приложения против статических инструментов при поиске нарушений чистой архитектуры. Пока это идея без проверки: датасет и разметка не выбраны.

## Почему

- Направление содержательное: статические инструменты видят только код, а в Spring архитектура времени выполнения (внедряемые бины, динамически вызываемые классы) может заметно отличаться. Через Actuator весь контекст отдаётся в JSON, это граф связей. Руководитель назвал подход очень интересным.
- Гипотезы теперь его собственные и проверяемые: динамический контекст улучшает результат LLM-подхода из статьи про evidence-based оценку; подход находит не меньше нарушений, чем тесты ArchUnit как baseline. В статье Recall не считали, это и есть пробел.
- Сужение до Java одобрено: статьи с открытыми репозиториями, на которых гоняли инструменты, можно использовать.
- Валидации пока нет, и это главный риск: на одном проекте проверка не работает, бенчмарки из статей могут не подходить для динамического случая, а подготовка данных сильно влияет на результат.

## Решения

| # | Решение | Обоснование |
|---|---------|-------------|
| Р1 | Только Java-проекты | Сужение одобрено |
| Р2 | Сравнивать на известном датасете, не меньше 30 проектов | Статистическая значимость; проще объяснить, откуда датасет |
| Р3 | Запасной вариант: синтетический датасет с внедрёнными ошибками, нужна литература о корректном внедрении и случайная выборка | Иначе скажут, что результаты подтасованы |
| Р4 | Сравнение со статическими инструментами достаточно, если динамических аналогов нет | Сначала выяснить, есть ли они (A12) |
