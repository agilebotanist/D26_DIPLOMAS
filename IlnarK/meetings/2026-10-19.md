# Ильнар Хасанов — встреча 2026-10-19

**Итог:** Тема сместилась к тому, насколько статические проверки типов в Python (MyPy, ty, Pyright, Pyrefly) видят последствия изменения доменной модели в ORM-проектах, и в ней уже есть вклад сверх сравнения. Формулировка пока не сфокусирована: сегодня подать широко, к прогону 26 октября переписать.

## Почему

- Вклад есть: не только сравнить чекеры, а добавить анализ blast radius, статический (SQLAlchemy, ORM, кодовая база) и агентный, и отдельно покрыть то, чего чекер не видит по определению: динамические атрибуты, raw SQL.
- Проверка намечена правильно: большие проекты с GitHub, синтетические изменения, сравнить, сколько ошибок нашёл MyPy и сколько нашли мы. Но ошибки надо сеять по правилам mutation testing, иначе скажут, что накидали только удобные.
- Литература начала работать на тему: ORM не проверяет типы (2016), динамические атрибуты MyPy видит плохо, но встречаются редко (2022), Instagram за 8 месяцев покрыл типами только половину кодовой базы. Нерелевантное (35 проектов про библиотечные зависимости) отсеяно.
- Показанная формулировка («Recall of current static analysis tools in detecting the impact of domain model changes…») не принята: первая часть непонятна, recall здесь лишний, нет ответа «зачем».

## Решения

| # | Решение | Обоснование |
|---|---------|-------------|
| Р1 | Тема строится на трёх вопросах: что изучаем, зачем, какой результат | Иначе формулировка остаётся перечнем инструментов |
| Р2 | Результат — инструмент, который делает то, чего нынешние чекеры не умеют, а не просто сравнение | Сравнения для диплома мало |
| Р3 | Ошибки в датасет вносятся по подходу mutation testing: заданные типы, частоты, корректная рандомизация | Иначе сравнение «наш подход лучше» некорректно |
| Р4 | Тему подать сегодня в Moodle в любом виде, руководитель одобрит, потом уточним | Регистрация не должна ждать идеальной формулировки |
