INTRODUCTION
What counts as a security requirement?
RQCODE  |  PhD defense

Definition adopted in this thesis
A security requirement is a detailed requirement that implements an overriding security policy by constraining the system to preserve the confidentiality, integrity, and availability of its assets against identified threats.
Confidentiality
Information is not made available or disclosed to unauthorized individuals, entities, or processes.
Example: Client–server traffic must be encrypted with TLS 1.2 or higher.
Integrity
Accuracy and completeness of information.
Example: An update package must be rejected unless its digital signature verifies.
Availability
Accessible and usable on demand by an authorized entity.
Example: The login service must be available for 99.9% of each calendar month.
Definition: D. Firesmith, “Engineering Security Requirements”, Journal of Object Technology 2(1), 2003, extended with the CIA triad.
Confidentiality, integrity, availability: ISO/IEC 27000:2018, Information technology — Security techniques — Information security management systems — Overview and vocabulary.

BACKGROUND SYNTHESIS  •  PROBLEM STATEMENT
Four motivation drivers of the thesis
RQCODE  |  PhD defense
09 / 46
MD1
Precision of NL requirements
NL security requirements are often imprecise, ambiguous, incomplete, or inconsistently stated. As a result, they cannot be automatically checked against the systems they describe.
MD2
Traceability and evolution
Security standards such as ISO/IEC 27001, OWASP, and DISA STIG are regularly revised. When traces between standards, security requirements, verification artifacts, and implementation artifacts are managed manually and outside version-controlled code, these artifacts drift apart.
MD3
Reusability
Security requirements are highly context-dependent. Generic templates must be adapted before they can be applied, while project-specific requirements are distributed across artifacts and projects, which makes their coordinated evolution difficult to manage.
Evidence cited in the thesis problem statement: P1 Zhao 2021; Guo 2025. P2 Mubarkoot 2023; Castellanos 2022. P3 Sönmez 2021.

public class AccountLockout extends Requirement {

  public AccountLockout() {
    super("Lock the account after five "
        + "consecutive failed logins.");
  }

  @Override
  public CheckStatus check() {
    if (!stateObservable())
      return CheckStatus.INCOMPLETE;
    return isLocked() ? CheckStatus.PASS
                      : CheckStatus.FAIL;
  }
}

RQCODE  •  LIGHTWEIGHT FORMALIZATION
Lightweight formalization: four defining properties
RQCODE  |  PhD defense
19 / 46
Lightweight formalization is the specification of a requirement in a form precise enough for automated checking, while retaining four properties that distinguish it from full formal methods.
1
Selective scope
Chosen properties of a requirement are formalized, not a complete model of the system.
In RQCODE: one class checks the property its statement expresses.
2
Executable checking in place of proof
Conformance is decided by executing code, not by discharging proof obligations.
In RQCODE: check() returns PASS, FAIL, or INCOMPLETE.
3
Programming-language notation
The requirement is written in a general-purpose language already used for development.
In RQCODE: requirements are Java classes.
4
Low adoption cost
The representation fits ordinary environments and toolchains, with no dedicated formal-methods infrastructure.
In RQCODE: classes live in the codebase and run with standard Java tools.
Partially formal: more precise than NL, less complete than a mathematical specification.
Related to seamlessness (continuity of notation across the lifecycle) but not the same property: it concerns how completely a requirement is formalized. The thesis defines the term because “lightweight” has no shared definition (Zamansky et al., 2018).
2:00. The formalization process in BPMN, as described in the thesis. Two swimlanes: Requirements, and Implementation and verification. 1 Requirements verification takes the NL requirements and produces a requirements hierarchy. 2 Refinement maps the hierarchy to classes and produces the class diagram. 3 Implementation turns the class diagram into implemented requirements in Java code, each with an executable check(). 4 Verification runs the checks against the system under verification. The 'Verified?' gateway returns a negative outcome to Implementation and ends the process on a positive one, so verification is repeated whenever the implementation changes. Keep the two verification activities apart: Requirements verification concerns the requirements; Verification concerns the system. The process is selective: with atomic, precise input, Implementation and Verification alone can be enough. BPMN is only the notation used to describe the process; it is not part of RQCODE. The diagram is rebuilt with native shapes from the thesis description; check the operation and artifact names against the final figure in the manuscript.
