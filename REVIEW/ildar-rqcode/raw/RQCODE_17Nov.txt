THE PROBLEM  •  THESIS PROBLEM STATEMENT
Problem statement
RQCODE  |  PhD defense

Core problem: Security requirements are usually specified in Natural Language (NL) and maintained as documentation artifacts, whereas their implementation, verification, and enforcement rely on executable software artifacts. The lack of a unified representation between these two worlds creates a persistent gap that hinders automated verification, traceability, evolution, and reuse of security requirements.

P1
Precision of NL security requirements [3], [4]
NL often lacks the precision. 
Security requirements may therefore be ambiguous, incomplete, and inconsistent, leading to different interpretations among stakeholders.
P2
Traceability and evolution [5], [6]
Trace links between standards, security requirements, verification artifacts, and implementation artifacts are managed manually and outside version-controlled development environments, these artifacts can gradually drift apart. 
P3
Reusability [7]
Security requirements are often highly context-dependent.
Security requirements are scattered across documents, repositories, and projects that limits their reuse and making their maintenance and evolution difficult.
[3] L. Zhao et al., “Natural language processing for requirements engineering: A systematic mapping study,” ACM Computing Surveys, vol. 54, no. 3, 2021.
[4] J. L. C. Guo et al., “Natural language processing for requirements traceability,” in Handbook on Natural Language Processing for Requirements Engineering, A. Ferrari and G. Ginde, Eds. Springer, 2025, pp. 89–116.
[5] M. Mubarkoot et al., “Software compliance requirements, factors, and policies: A systematic literature review,” Computers & Security, vol. 124, art. 102985, 2023.
[6] J. P. Castellanos Ardila et al., “Compliance checking of software processes: A systematic literature review,” Journal of Software: Evolution and Process, vol. 34, no. 5, e2440, 2022.
[7] F. Özdemir Sönmez and B. Günel Kılıç, “Reusable security requirements repository implementation based on application/system components,” IEEE Access, vol. 9, pp. 165966–165988, 2021.

1:30. The thesis defines the term because 'lightweight' has no shared definition in the literature (Zamansky et al., 2018) and because notation-based classifications such as Bruel et al. (2021) do not say how completely a requirement is formalized. Definition: the specification of a requirement in a form precise enough for automated checking, while retaining four properties. Selective scope: chosen properties, not a complete model. Executable checking in place of proof: conformance is decided by running code. Programming-language notation: a general-purpose language already used for development. Low adoption cost: ordinary environments and toolchains, no dedicated formal-methods infrastructure. Result: partially formal, more precise than NL and less complete than a mathematical specification. Likely question: how does this differ from seamlessness? Seamlessness is continuity of notation across requirements, design, implementation, and verification; lightweight formalization concerns how completely a requirement is formalized. Check before the defense: an earlier analysis of the manuscript noted that, because of the programming-language property, lightweight formalization can also be read as a specialization of seamlessness. Use the relation stated in the final manuscript, and keep the slide wording consistent with it.

PROBLEMS AND OPTIONS  •  LIGHTWEIGHT FORMALIZATION
Lightweight formalization
RQCODE  |  PhD defense
Lightweight formalization is the specification of selected properties of a requirement in a precise and machine-checkable form that enables automated checking, without constructing a complete formal model of the software system.
1
Selective formalization
Chosen properties of a requirement, not the whole system.

2
Execution-based checking
Compliance is decided by running code, not by proof or model checking.

3
Programming-language representation
Written in a language already used for development.

4
Integration with development practice
Specified, checked, and maintained with familiar tools; no formal-methods infrastructure.

Does a PASS prove the rule? What does INCOMPLETE prevent?
RQCODE  |  PhD defense
Backup  56
No proof: a PASS reports that the implemented condition held on what the check observed, when it ran.
PASS
Execution, not proof: no claim for all possible system states (§4.3.6, §6.2.2).
Only as reliable as the observation and the check’s parameters.
INCOMPLETE
Separates “cannot determine” from “violated”: missing information, a step that cannot run, a network failure or a timeout (§4.1.3).
Such cases are not recorded as violations.
Before any check
lastCheckStatus starts as INCOMPLETE: no verdict until a check has run (Listing 4.1).

public class AccountLockout extends Requirement {

  public AccountLockout() {
    super("Lock the account after five "
        + "consecutive failed logins.");
  }

  @Override
  public CheckStatus check() {
    if (!stateObservable())
      return CheckStatus.INCOMPLETE;
    return isLocked() ? CheckStatus.PASS
                      : CheckStatus.FAIL;
  }
}
PASS
The account is locked.
FAIL
The account is still unlocked.
INCOMPLETE
The counter or lock state cannot be observed.
The statement and its check live in one class; the verdict is only as trustworthy as the observation behind it.

Lightweight formalization is not a lightweight formal method

Dimension
Lightweight formal methods
Lightweight formalization (RQCODE)
Language partiality
A formal language may be restricted to a decidable or manageable subset.
No dedicated formal language: a general-purpose programming language.
Modeling partiality
Only selected aspects of a system are formally modeled.
Only selected properties of a requirement are made precise enough for executable checking; no complete formal model.
Analysis partiality
Analysis is restricted in scope, for example a bounded search space.
Requirement-specific checks are executed; no proof, no exhaustive search of a state space.
Composition partiality
Formal and informal artifacts coexist.
The natural-language statement and the executable check live in the same artifact.
RQCODE does not claim to be a lightweight formal method: executing check() gives the result under the observed conditions, not a proof for all states.

BACKUP  •  QUESTION
Why only parent and child, and why conjunction?
RQCODE  |  PhD defense
Backup  70
RQCODE uses one relation between requirements, parent and child, mapped to inheritance; a composite requirement passes only if all its parts pass. Richer relations were not modeled.
In SysML
Derivation, refinement, generalization and containment relate requirements.
Each relation carries its own meaning for tracing and analysis.
In RQCODE
Parent and child only, mapped to class inheritance.
A composite checks its parts and combines the results by conjunction.
In the ATM example, one link appears as both composition and inheritance.
Possible extension
Alternatives such as success, wrong PIN or insufficient funds need “if precondition, then outcome”, not AND.
A mapping to SysML v2 requirement relations. Neither was evaluated.
